# Pouch 学习看板 · Spec

Status: ready-for-agent

> 本 spec 由用户已在本仓库 `docs/00~05` 六份详细设计中达成的全部决策综合而成（详见 docs/ 目录，架构决策 ADR-001~012 见 `docs/00-总览与技术选型.md` §0.5）。本文件是对该方案的 PRD 式整理与发布，不引入新的需求来源。

---

## Problem Statement

用户在持续学习过程中，随手产生的灵感、问题、碎片知识和"要做的事"散落在各种地方，缺少一个统一的、结构化的落点：既不方便回看，也不会主动"跳出来"提醒自己哪些事情长期停滞。与此同时，心愿单（想买的书、器材等）的金额跟踪散落在各处，缺少"总心愿 / 已花 / 还差"这三个关键数字的即时汇总。

用户需要：

1. 一个**本地运行、零依赖部署**的记录系统（单用户，无登录、无云端），数据以**纯 JSON 文件**落盘，可用文本编辑器直接修改，可纳入 Git 版本管理。
2. 一个本地 Web 看板，把散落的记录聚合呈现：总量统计、待办完成率、心愿单金额汇总、随机抽取沉底的记录、长期未推进的陈旧提醒。
3. 一个统一的浏览与编辑入口，支持按类别、学科、标签、状态、时间筛选，支持 Markdown 正文与追加式笔记。

## Solution

**Pouch** 是一个单用户、本地运行（`127.0.0.1:8787`）的学习记录看板：

- **存**：四个记录类别（灵感 / 问题 / 碎片知识 / 要做的事）+ 独立的心愿单，各一个 JSON 文件，共 5 个文件，均含版本字段与近 50 份写入前备份。写入采用"临时文件 + 原子 move + force 刷盘"，保证任何时刻断电/崩溃后数据文件要么完整、要么可从备份恢复。
- **看**：原生 HTML/CSS/JS 前端（无框架、无构建步骤），四个页面：
  - 首页看板 `index.html`——六个区块：类别计数、待办完成率环形图、心愿单金额汇总、随机回顾、碎片知识构成环、陈旧提醒。
  - 分类列表页 `list.html`——按类别浏览，筛选条件按类别动态变化（学科/标签/状态/截止日/关键词/排序/分页）。
  - 详情页 `detail.html`——Markdown 只读渲染 + 编辑态，追加式笔记区，标签管理，类别相关的状态切换主按钮，跨类别变更支持。
  - 心愿单页 `wishlist.html`——条目管理、勾选已购（金额删除线）、三项汇总实时联动、`↑`/`↓` 邻位交换排序、快速新增。
- **后端**：Java 21 + JDK 自带 `HttpServer`，唯一第三方依赖是 Gson。分层清晰：路由 → Handler（HTTP 语义）→ Service（业务规则/校验/统计）→ Store（文件读写/锁/原子写/备份/内存索引）。
- **数据一致性**：内存为查询源（启动全量载入 + `byId` 哈希索引 + `ordered` 有序列表，每文件独立的读写锁），写时回刷整文件；唯一的跨文件写（变更类别）采用"先加后删 + 固定加锁顺序 + 启动时重复 id 检测"策略。

## User Stories

1. 作为用户，我希望打开本地看板时一眼看到四个类别各自的记录总数，以便快速判断当前各类学习的体量分布。
2. 作为用户，我希望看到「要做的事」中已完成与未完成的占比环形图（中心显示完成率百分比），以便直观感受待办完成进度。
3. 作为用户，我希望待办完成率的分母只统计"我承诺要做的事"——已取消的事项不计入完成率，也不画进环图，而是以小字提示「另有 N 项已取消」，以便避免已放弃的承诺虚增我的完成率负担或未完成压力。
4. 作为用户，我希望在完成率"无定义"（一条待办都没有，或全部已取消）时，页面显示「暂无待办」而不是一个 0% 的空环，以便避免被误导成"有大量未完成事项"。
5. 作为用户，我希望在首页只看到心愿单的三个关键数字（总心愿金额 / 已花掉金额 / 还差金额）和一根"已花占总额"的进度条，而不是完整清单，以便"一眼看完"首页的同时被"还差多少钱"这个事实本身影响消费决策。
6. 作为用户，我希望有三个数字构成的恒等关系：总心愿金额 = 已花掉金额 + 还差金额，且该关系由后端统一计算、前端只负责展示格式（元），以便三处口径永不漂移。
7. 作为用户，我希望在首页之外另有一整页（心愿单页）可以完整管理条目：查看列表、勾选/取消勾选"已购"、快速新增、写一句备注（如"等打折"），以便首页保持轻量而条目管理又有专门的专注场所。
8. 作为用户，我希望勾选"已购"后，该条金额加删除线并显示实现日期，但**条目本身不消失**，以便保留"已实现"的历史，让这个页面同时是一个消费"账本"而不只是一个待办清单。
9. 作为用户，我希望能在心愿单页对条目做上下两档的邻位排序（`↑` / `↓` 按钮），而不是复杂拖拽，以便在手机上也能用按钮调整后，且不需要为此引入拖拽库带来的移动端兼容问题。
10. 作为用户，我希望"默认按创建时间（先加的在前）"与手动排序能够共存——未手动调整过之前两者等价，一旦调整过就以后者为准——以便我既不用一上来就操心排序，也能在自己想调整时自由调整。
11. 作为用户，我希望在心愿单页删除某个条目时必须二次确认，并明确提示"删除后可从 `data/.backup/` 恢复"，以便我不小心删掉真正买过的东西时仍有挽回通道，同时不影响我主动清理误录入。
12. 作为用户，我希望每次操作后（新增/勾选/取消勾选/排序/删除）首页顶部三个数字与进度条、以及心愿单页顶部的三个数字与进度条，**立即**联动更新而无需手动刷新页面。
13. 作为用户，我希望首页有一个"随机回顾"区块，可以在"灵感"与"知识点"两个 tab 之间切换，各显示一条记录的标题、正文摘要，并提供"换一条"按钮，让沉下去的旧记录能**主动浮上来**，而不需要我去列表里翻找。
14. 作为用户，我希望"换一条"在一轮里不会重复抽到同一条，直到把当前池子遍历完一次后才重新开始，以便复习效果更均匀，而不是连续看到同一条。
15. 作为用户，我希望"灵感"与"知识点"两个 tab 各自维护独立的"已看列表"，且切换 tab 时**不重新抽取**，而是显示该 tab 上一次抽到的内容，以便我"换一条"后切走再切回来，刚才看到的那条不会消失。
16. 作为用户，我希望同一类记录中"已被归档/放弃"的灵感不会出现在随机回顾里，而"已掌握"的知识点**仍会**出现，因为前者已不需要再看，后者仍需复习。
17. 作为用户，我希望当某类记录池为空（如一条灵感都没记过，或灵感全部归档）时，随机回顾区块显示专门的空态引导文案（如"还没有灵感，去记一条"而非空白卡片或错误提示），并能跳转到记录新建入口。
18. 作为用户，我希望首页还有一个"碎片知识构成"环形图，可以用滑块在"按学科"与"按标签"两个维度之间切换，直观看到我在什么学科 / 什么标签上投入最多。
19. 作为用户，我希望当标签维度超过 8 个候选时，只展示计数最高的前若干个标签，其余合并成一片"其他 N 个"，以便环形图不会因为标签无限膨胀而变成看不清的一团；同理学科维度超过上限也做相同聚合。
20. 作为用户，我希望"其他 N 个"这一片固定用中性灰色，不与主题配套色轮换，以便它在视觉上退后，不与设计配色争抢注意力。
21. 作为用户，我希望"按标签"维度的请求只在滑块切到该维度时才发送，而不是首屏就同时请求两个维度的数据，以便首页首屏请求数更少、更快。
22. 作为用户，我希望首页还有一个"陈旧提醒"区块，专门列出长期未被推进的记录（标题、类别徽标、当前状态、停滞天数），按停滞天数降序展示，把"你正在忽视什么"这个事实单独立出来呈现，而不是淹没在某个列表的排序里。
23. 作为用户，我希望"陈旧"的判定规则按类别区分——如未解决的问题 30 天、无截止日的待办 21 天、灵感 60 天，而碎片知识本身不参与（它的复习已由随机回顾承担，不算重复提示），且带截止日的待办也不参与（由截止日本身驱动提醒），以便"陈旧"这个概念对不同性质的记录有各自准确的含义，而不是一个粗暴的统一阈值。
24. 作为用户，我希望在陈旧提醒区块下方看到各类别超过阈值的条数分布（如"未解决问题共 12 个"），而不是只看前 10 条清单，以便即便清单被截断，我也能感知到问题的真实规模。
25. 作为用户，我希望当我在详情页随手改一个字、或补一条笔记，就把这条记录从陈旧列表里顶出去——因为"推进时间"直接使用"最后修改时间"，这在直觉上就代表"你确实碰过了它"。
26. 作为用户，我希望陈旧提醒区块为空时显示"近期都在推进，没有陈旧记录"这种明确的正面反馈，而不是显示空白或隐藏区块，以便我确认"现在没有需要担心被遗忘的事情"。
27. 作为用户，我希望在列表页用左侧导航切换四个类别，并看到每个类别当前的计数徽标，以及在主导航旁单独有一个"心愿单"入口。
28. 作为用户，我希望列表页顶部筛选栏**按当前类别动态变化**——通用项是关键词搜索（标题 + 正文）、标签多选、状态、排序（时间/更新时间/标题）、每页条数；碎片知识额外有**学科**下拉筛选（支持按 `/` 分层显示的层级下拉）；"要做的事"额外有截止日期范围筛选——以便不同类别看到自己天然需要的筛选维度，而不是一个永远全开的、杂乱的筛选面板。
29. 作为用户，我希望选择一级学科（如"数学"）作为筛选条件时，匹配结果是**层级前缀**语义——包含该学科及其所有子学科（如"数学/线性代数"），以便我不会因为没去点选具体子学科而漏掉记录。
30. 作为用户，我希望学科下拉里显示的每个层级的**条目计数**与按该学科实际筛选出的结果数**严格一致**（例如选"数学"，下拉里显示 15，筛选后分页器也显示 15 条），以便我对数据量有可校验的预期，而不是"下拉说 15 个、结果区却给我 12 个"这种口径不一致的困惑。
31. 作为用户，我希望搜索支持中文关键词，且触发时机是输入防抖（约 250ms）或回车立即执行，以便我不需要每敲一个字就等一次请求。
32. 作为用户，我希望切换任何筛选条件后，页码自动回到第 1 页，而不是停留在之前某个可能已经没有数据的页码上，以便避免"明明筛出了结果却停在空白第 7 页"这类常见体验陷阱。
33. 作为用户，我希望在列表的最后一页删掉一条记录后，自动回退到新的有效最后一页，而不是停在现在为空的那一页上。
34. 作为用户，我希望列表项展示：标题、正文前两行去 Markdown 标记后的摘要、标签、状态徽标、相对时间（以及"要做的事"的逾期提示），点击整行进详情页。
35. 作为用户，我希望直接在列表行上做状态切换（如勾选完成），操作成功后该行若在当前筛选条件下不再匹配（如按"待办"状态下勾选完成），会以淡出的方式从列表中移除；失败时复选框自动回滚并弹出错误提示，以便界面与真实状态始终一致，而不需要等整页刷新。
36. 作为用户，我希望列表页区分两种"空"：一条记录都没有（显示"还没有X，去记一条吧"+ 新建按钮）与有记录但当前筛选条件无匹配（显示"没有符合条件的记录"+ 清除筛选按钮），以便我知道该去创建内容还是该放宽筛选。
37. 作为用户，我希望在列表页右上角可以直接点"+ 新建"，弹出一个模态框快速录入标题（及当前类别需要的专有字段），不必先进入详情页再补录入，以便随手记一条的门槛足够低。
38. 作为用户，我希望进入详情页后，正文以 Markdown 只读方式渲染（标题、列表、代码块、链接等都正确显示），并提供"编辑"按钮切换到文本编辑态、保存后重新渲染，以便我只在需要修改时才进入编辑干扰，其余时间看到的是干净的文章排版。
39. 作为用户，我希望在编辑态下内容未保存时切换到只读态或取消，编辑内容被完整丢弃、回退到原值（而不是把改了一半的内容悄悄保存），以便"取消"的语义是自洽的，不会让我怀疑刚才到底存没存上。
40. 作为用户，我希望在编辑态下未保存就关闭标签页时，浏览器会弹出"您有未保存的内容"确认提示，以便至少有一个挽回的提示窗口，而不是内容无声消失。
41. 作为用户，我希望多次编辑之间用一个"草稿深拷贝"来暂存正在编辑的内容，而不是直接覆盖渲染源数据，以便即使我在编辑过程中反复点和取消、保存，原始终端数据始终是一个干净的基线，不会被半成品污染。
42. 作为用户，我希望在详情页可以随时追加带时间戳的新笔记（多条），每条笔记可以单独编辑或删除，而正文（原 `content`）不会被笔记操作触碰，以便"事后补充想法"有一个专门的落点，与"记录本身是什么"这两件事在存储和展示上都清晰分离，且不会被误操作整段覆盖。
43. 作为用户，我希望追加/编辑/删除笔记时，父记录的"最后修改时间"也随之更新，以便也让"最近有没有被推进"这个信号正确反映笔记活动（这与陈旧提醒的判定直接相关）。
44. 作为用户，我希望追加或编辑笔记的接口**只支持一条条操作，不支持整体替换**整个笔记数组，前端也因此没有"全选笔记一键删除/覆写"这类危险入口，以便一次误操作不会把一整段历史笔记全部冲掉。
45. 作为用户，我希望在详情页的标签区增加、删除标签，并在输入时获得已有标签的自动补全提示（datalist），以及一条明确的"标签不能包含 `/`"校验（学科才用 `/` 分层，标签是自由文本维度），以避免两套分类语义混用。
46. 作为用户，我希望状态切换的主按钮文案随当前类别与当前状态变化——"要做的事"未完成时按钮是"标记完成"、已完成后变成"标记未完成"；"问题"是"标记已解决"（已解决后引导我把答案补充到正文或笔记里）；"碎片知识"是"标记已掌握"；"灵感"是"归档"——以便按钮始终表达"我接下来想做的那个动作"，而不是一个抽象的"编辑状态"。
47. 作为用户，我希望把一条"要做的事"标记为"完成"时系统自动记录完成时间，回退为"未完成"时自动清空这个时间，且我不需要、也不应该在请求里手动传这个字段，以便"完成时间"是一个可信的服务端事实，而不是可以被任意改口的客户端数据。
48. 作为用户，我希望把一条记录从一个类别改为另一个类别（例如把一条已经想清楚的"问题"沉淀为"碎片知识"），系统的 `id` 保持不变（这样详情页链接仍然有效），目标类别必填的专有字段必须补齐（如转"碎片知识"必须给学科），而原类别不再适用的专有字段会被自动清除（如在"要做的事"里的截止日期、优先级在转成其他类别后自动消失），以便"变更类别"是一个清晰、可预期、无残留脏字段的操作。
49. 作为用户，我希望在详情页的元信息面板看到创建时间、更新时间、状态、以及（如适用）学科等只读信息，以及一个"置顶"开关，以便置顶的记录能在列表默认排序中优先出现。
50. 作为用户，我希望可以在详情页删除记录，但入口要弱化（如页面底部小字链接）并强制二次确认，以便不容易误触删掉真正有价值的记录。
51. 作为用户，我希望删除记录是一个**硬删除**（不是"软删除+隐藏"），但每次写入前系统会自动在备份区留下一份当时的文件快照（保留最近约 50 份/文件），并且如果我真的删错了，我可以打开备份区找到对应时间点的手动恢复，以便"删除"既足够直接（不用到处维护"已删除"过滤逻辑），又不至于完全没有退路。
52. 作为用户，我希望当某个或多个数据文件在启动时因写入中断等原因损坏时，系统自动从最近备份恢复该类别的数据，把损坏的文件保留成另存名供我排查，且**其他类别不受影响**、服务照常启动，页面顶部出现橙色告警横幅提示我"某文件已从备份恢复"，以便我在不丢失其他数据的前提下知道发生了什么，而不是整个应用直接崩溃或静默丢数据。
53. 作为用户，我希望数据文件是**纯 JSON、UTF-8、带可读缩进**的文本，我可以用任何文本编辑器直接打开、修改、查 diff，且中文显示正常，以便"数据是我的"这件事在物理层面成立——它不依赖某个专有格式或专有软件的封闭存储。
54. 作为用户，我希望数据文件可以整体被 Git 追踪，每条记录的变更历史可追溯（如用 `git log -p` 查某条记录是何时被改成什么样的），以便误改、版本对比、跨时间点恢复都有据可查，且完全不需要数据库。
55. 作为用户，我希望后端服务只在 `127.0.0.1` / 本机回环地址上监听，不对外暴露端口，且没有任何登录/鉴权机制，以便"本地单用户工具"的边界是不言自明的——这是本地工具，不是需要防外部访问的 Web 应用。
56. 作为用户，我希望后端的 HTTP 行为有丰富的能力（路径参数、路由、静态文件托管、CORS 之外的常规能力）但不依赖第三方 Web 框架（如 Spring），以便我本机只需要一个 JDK 和一个小小的 JSON 库 jar 就能跑起来，不牵扯庞大依赖树或构建工具。
57. 作为用户，我希望前端没有任何构建步骤（不用 npm、不用打包工具），改完代码刷新浏览器即可生效，以便"学习一个项目"这件事本身不被"配置环境"拖住节奏。
58. 作为用户，我希望前端使用设计 Token（CSS 自定义属性）统一管理颜色、间距、字号、圆角、阴影、动效，并且任何页面样式不得写死具体数值（杂志毕业：颜色/间距/圆角都不许在组件层硬编码），以便将来调整视觉风格时只需要动一个 Token 文件，而不是翻遍四个页面。
59. 作为用户，我希望界面支持亮色与暗色两套主题，默认跟随系统偏好，同时提供手动切换，且所有数据可视化（如环形图）的颜色在切换主题时也要跟着变，以便暗色环境下不会有一块突兀的亮色图表。
60. 作为用户，我希望界面在手机浏览器宽度下是响应式的（单列堆叠，无横向滚动条），以便在手机上查看（虽然不打算在手机上重度编辑）至少是能看的。
61. 作为用户，我希望整个界面（包括按钮、模态框、表单、图表）在键盘 Tab 键下焦点可见、可操作、顺序合理，以便键盘操作是一等公民而不是二等体验。
62. 作为用户，我希望界面上出现的所有**机器可读枚举值**（类别、各状态文案、状态操作按钮文案、类别专属表单字段清单、类别是否参与随机回顾等）都通过元数据接口动态获取，而不是前端硬编码，以便将来新增一个类别或调整某个状态的展示名时，只需要同步改后端枚举定义而不是同时翻改前端多个文件。
63. 作为用户，我希望在正文中粘贴或输入的内容（Markdown 渲染后）必须经过 HTML 净化（DOMPurify）才能插入页面，以便粘贴的网络内容里可能携带的脚本不会被执行，即使这是单用户本地应用也要有这条 XSS 防线。
64. 作为用户，我希望前端发起网络请求的代码全部收口在一个 `api.js` 部门里，页面级脚本不直接拼 URL、不直接 `fetch`，以便将来接口变化时只改一处，也便于统一处理错误响应的分支（如针对不同错误码高亮对应输入框）。
65. 作为用户，我希望页面代码层面不做任何字符串拼接 HTML 的写法（除了极少数确实需要的 Markdown 渲染结果），一律通过 DOM API 创建元素，以便从机制上避免 XSS，而不只是靠"小心点"。
66. 作为用户，我希望当后端服务没启动（或崩溃）时刷新页面，看到的是"无法连接到本地服务器"这类**友好的错误卡片**，而不是白屏、控制台一堆看不懂的报错，以便我知道要去检查后端而不是怀疑前端代码坏了。
67. 作为用户，我希望服务启动时若端口被占用，给出明确的错误提示并提示我可以用参数换一个端口，而不是无声失败。
68. 作为用户，我希望可以通过启动参数（数据目录、静态资源目录、端口）覆盖默认路径与端口，以便同一份代码可以在不同目录/不同端口下运行，且能方便地为测试准备一份干净的临时数据目录而不污染真实数据。
69. 作为用户，我希望后端提供健康检查接口，返回服务启动时间、实际使用的数据目录、各文件条目数，以及启动过程中产生的**非致命告警**（如某文件从备份恢复），且前端首页应把这些告警渲染成页面顶部横幅，以便排查"改了数据文件但页面上没生效"这类问题时有据可查。
70. 作为用户，我希望所有 API 的错误响应使用统一、机器可读的结构（`code` + 人类可读的 `message`），且错误码在契约文档中有完整枚举（如 `invalid_type`/`invalid_status`/`invalid_subject`/`record_not_found`/`invalid_amount` 等），以便前端可以针对特定错误码做精准的界面处理（高亮对应输入框），而不是靠解析 `message` 字符串来猜错误类型。
71. 作为用户，我希望在保存（新建/编辑/删除/勾选）遇到服务端 5xx 错误时，前端**保留我刚刚填写的所有表单内容**，只提示"保存失败，请重试"，而不是把输入框清空或回滚到旧值，以便错误是临性的（网络抖动，实际上本地极少发生）时我可以直接重试，而不需要重新打一遍字。
72. 作为用户，希望所有金额在任何界面（首页、心愿单页）的展示都统一格式化为"元"（保留两位小数、千分位分隔），且所有涉及金额的加减运算都在**整数分**上完成、只在展示层转换为元，以便"还差的钱数"永远是一个精确的整数分换算结果，不会出现 `1234.5600000000002` 这类浮点尾差。
73. 作为用户，我希望记录正文最大长度、笔记最大长度、标签最多数量、心愿条目单笔金额上限等边界，都有明确的、被后端强制执行的校验与友好的报错，而不是写到后面才发现某个字段静默被截断。
74. 作为用户，作为"记了一条"这件事本身，我希望拖动一条 `pinned`（置顶）为真的记录，能在列表默认排序里优先于同类别的其他记录出现，以便重要的、正在跟进的少数记录不会被淹没在按时间排的长列表底部。
75. 作为用户，我希望详情页的"返回"按钮先尝试浏览器历史回退（`history.back()`），历史不可用时再回退到"来源页"参数指向的 URL，最终兜底到默认列表页，以便不管我从哪里进来、隔了多久再点返回，都有一个合理的去处，而不是我来的筛选条件全丢了。
76. 作为用户，我希望"问题"类别的详情页在我把它标记为"已解决"后，界面会引导我把答案补充到正文或笔记里（因为本产品的理念是问题只有在"答案被写下来"之后才算真正解决，而不是仅仅打了个勾），以便我的"已解决"记录未来翻出来时，答案本身是能被看到的。

> 说明：用户故事是为方案中已被 `docs/00~05` 逐条确认的决策逐条展开，偏多、偏细是刻意的——这份 spec 面向的读者是"要依据它实现整套系统的实现者（人或 agent）"，而非路人。

## Implementation Decisions

以下决策继承自 `docs/00-总览与技术选型.md` 中 ADR-001~012，此处仅做要点重述与补充，**不引入与 ADR 冲突的新决策**：

1. **技术栈**：Java 21 + JDK 自带 `com.sun.net.httpserver.HttpServer`，唯一第三方库为 Gson 2.11.0（单 jar 手动放入 classpath 而非通过 Maven/Gradle 管理）；前端为原生 HTML/CSS/JS，本地化引入 Chart.js、marked、DOMPurify 三个库（不走 CDN），无任何前端构建步骤（ADR-001/006）。
2. **数据模型**：四种记录类别（灵感 / 问题 / 碎片知识 / 要做的事）共用同一个"记录"模型结构，用 `type` 字段区分，类别专有字段（如 `subject`/`dueDate`/`priority`/`doneAt`/`source`）在不适用时保持为"空且不出现在文件里"，而不是补一堆 `null`；心愿单条目是独立数据模型，**不复用**记录模型（ADR-003）。
3. **存储**：每种数据内容一个 JSON 文件，共 5 个文件位于数据根目录；每个文件带 `version`（当前恒为 1，为后续的字段结构迁移脚本预留判别依据）与文件级 `updatedAt`；内存中以"哈希索引（按 id）+ 有序列表（保序写回）+ 每文件独立读写锁"作为查询源，写操作触发"整文件回刷"（ADR-002）。
4. **原子性与备份**：所有写操作遵循"写前备份（保留每文件最近约 50 份）→ 内存中先完成序列化（失败不动磁盘）→ 写同目录临时文件 → force 刷盘 → 原子 rename 覆盖目标文件"的流程；启动时若某文件解析失败，按最新到最旧的顺序尝试备份恢复，恢复后损坏文件另存为供排查，**不崩溃、不影响其他文件**；启动时还会做一次全局重复 `id` 检测（是"先加后删"策略的兜底）。
5. **跨文件写（变更类别）**：全系统唯一需要跨两个文件的操作，采用"先在目标文件插入（保留原 id）→ 原子写目标文件 → 再从源文件删除 → 原子写源文件"的顺序（先加后删，而非先删后加——中断时"重复一条"比"直接丢失"更容易被发现和修复）；两把锁按类别枚举的固定声明顺序获取，避免死锁。
6. **分层职责边界（后端）**：路由/请求解析 → Handler（只做 HTTP 语义，不写业务规则）→ Service（业务规则、字段校验、统计口径）→ Store（文件读写、锁、原子写、备份、内存索引维护，不解析 HTTP、不校验业务字段）。
7. **API 契约**：19 个端点——健康检查、元数据三类（类别/标签/学科）、记录四类（列表查询带筛选、单条读取支持跨类别、部分更新 PATCH、删除）、笔记三类（新增/编辑单条/删除单条，**不提供整体替换笔记数组的端点**）、心愿单四类（列表带金额汇总/新增/部分更新/删除）、统计三类（总览、随机回顾、陈旧提醒）。统一 JSON（UTF-8）、ISO-8601 带时区时间、金额一律整数分（字段以 `Cents` 结尾）做传输、统一错误信封（`code` + `message`），除 `204` 外都有 JSON 响应体。
8. **PATCH 部分更新语义**：请求体中出现的字段才修改，未出现保持不变；显式传 `null` 表示"清空该可选字段"（区别于"不传"表示"不修改"）；对当前类别不适用的专有字段会被静默忽略（不报错）。
9. **完成/未完成与陈旧/随机/构成环等统计口径**（详见用户故事 2/4/13-26）：完成率仅统计"要做的事"，已取消项不进分母、不进环图；分母为 0 时返回 `null` 而非 `0`。陈旧提醒按类别区分参与条件与阈值（问题 30 天、无截止日待办 21 天、灵感 60 天、碎片知识与有截止日待办不参与），"推进时间"直接取记录最后修改时间（**备注：追加/编辑/删除笔记也会更新此时间戳**，这是刻意设计的跨文档依赖）。随机回顾仅"灵感"（限定未归档）与"碎片知识"（含已掌握）参与，排除/重抽机制在服务端。
10. **心愿单金额**：一律整数分（`long`）存储、传输与计算，只在展示层格式化为元；三项汇总由后端计算并随列表一起返回，前端不重复累加；"总心愿"含已购条目，保证"总 = 已花 + 还差"恒等式成立。
11. **变更类别（跨文件写的唯一入口）**：底层"先加后删"（先写目标文件、成功后再写源文件），两把文件锁按类别固定顺序获取以防死锁；中止时最坏结果是"一条可检测的重复记录"，而非"不可见的记录丢失"；启动时额外做跨文件重复 id 全局检测作为兜底。
12. **构建与运行**：不使用 Maven/Gradle，直接 `javac` 编译到输出目录、`java -cp` 运行；仓库内 PowerShell 脚本封装"编译 + 启动"与"单独启动"两种动作，并支持 `-Data` / `-Web` / `-Port` 参数覆盖数据根、静态根、端口（默认端口 8787），便于测试用临时数据目录隔离。
13. **前端约束**：`api.js` 是唯一发起 `fetch` 的地方，其余页面脚本不直接拼 URL；DOM 构造集中在一组辅助函数里，避免字符串拼接 HTML；所有颜色/间距/圆角等只引用设计 Token（CSS 自定义属性），组件层禁写死具体数值（杂志化）；亮/暗双主题 + 系统偏好跟随 + 手动切换；三个第三方库（环形图、Markdown、HTML 净化）本地文件引用，运行时不访问 CDN。

## Testing Decisions

**好测试的标准**：测对外可观测行为（HTTP 响应体、落盘 JSON 文件内容、页面呈现），而不测内部实现细节。本 spec 只设**一个 seam**：前端（呈现层）的人工 checklist + 全仓库反向搜索；后端行为不单设 seam，直接以 `docs/05` §5.1 阶段 1 交付的 `smoke-test.ps1` 与阶段 0-4 的"验收"清单项作为**实现期验收脚本**（不是测试 seam）使用。

**唯一 Seam：前端呈现层**（人工 checklist + 全仓库机械化反向搜索，不引入测试框架、不引入构建工具）：

1. **人工 checklist**：即 `docs/05` §5.1 每个阶段末尾的"阶段验收"清单项，从阶段 0（骨架跑通：一条命令启动、路径穿越防护 403、主题切换 + 刷新保持、五个 JSON 均为合法 JSON）到阶段 4（碎片知识构成环：top-N 聚合、`other` 灰色，按学科/按标签两种维度均可）；以及各阶段散见的交互验收项（如"停掉后端 → 刷新首页 → 显示友好错误卡片而非白屏或控制台报错""XSS 手工测试：正文写入 `<img src=x onerror=alert(1)>` 保存后渲染，**断言不弹窗**""切换暗色主题 → 环形图颜色跟随变化""手机宽度下单列堆叠、无横向滚动条""键盘 Tab 顺序与焦点可见性"）。每次修改涉及 UI 行为或交互的代码，必须重跑受影响阶段的全部清单项。
2. **全仓库反向搜索**（机械化文本断言，纯文本可判定、人工执行足够）：
   - `grep -Rn "innerHTML"` 全仓库：仅允许出现在 `web/js/dom.js` 中"显式做 `DOMPurify.sanitize` 后赋值"的那一处地方（或绝对禁止，若采用"完全不写 innerHTML"则断言零命中）；其他地方出现即违反用户故事 63/65。
   - `grep -RnE "#[0-9a-fA-F]{3,8}\b|rgb\(|rgba\("` 全仓库样式文件（`web/css/*.css`）：颜色字面量应**全部集中在** `tokens.css` 的 `:root` 定义区；`layout.css`、`pages.css` 或其他样式文件中不得出现颜色字面量（组件层必须引用 `var(--...)` Token），违反即违反用户故事 58。
   - `grep -Rn "fetch\b"` 全仓库前端 JS（除 `web/vendor/` 外）：仅允许出现在 `web/js/api.js`，不得在 `index.js` / `list.js` / `detail.js` / `wishlist.js` / `dom.js` / `theme.js` 里直接出现，违反即违反用户故事 64。
3. **后端**不单独立 seam：
   - `docs/05` §5.1 阶段 1 交付的 `smoke-test.ps1` 是**实现期验收脚本**（真实 HTTP + 真实临时数据目录），每次涉及 API 行为的代码改动后必跑，不作为测试 seam 记录。
   - 阶段 1 验收清单中的手工项（如"手动把 `todos.json` 改成非法 JSON → 重启 → 控制台打印恢复告警 + 生成 `.corrupt` + 服务正常启动""手动杀掉服务进程模拟崩溃 → 重启 → 数据完整"）属于验收清单，同样不单列。
   - 之所以不单独抽一个"内存版后端"做 Seam：真实故障形态（写入中断、部分文件损坏）依赖真实的文件系统时序，抽一个 mock 层会**掩盖**故障；且 API 冒烟脚本的数值断言（doneAt 联动、完成率口径剔除 cancelled、心愿恒等式 total = spent + remaining、随机不重复、学科前缀匹配）已经内嵌到脚本里，已是最外层可观测行为。

## Out of Scope

以下事项在 `docs/00` ADR 中已明确列为"非目标"，本次整理中逐项确认仍不进入本次实现范围；列出来是为了防止实现时误以为"顺手就能加"而把范围撑爆：

- 用户体系：注册、登录、鉴权、多用户、权限、多租户。
- 同步与协作：跨设备同步、云端存储、WebDAV/Syncthing、多端冲突合并、协同编辑（本产品的数据同步策略就是"整个文件夹拷来拷去"，见 `docs/05` §6.3）。
- 高级搜索：全文检索引擎（Lucene/ES 级别）、拼音/分词/同义词、跨类别高亮聚合搜索。当前搜索只做内存遍历 + 子串匹配。
- 附件与媒体：图片/文件上传、缩略图生成、独立的媒体存储空间（正文可以引用已有本地图片的相对路径，但系统本身不提供上传、不管理媒体文件的存储与生命周期）。
- 平台形态：原生移动 App、PWA 离线能力、桌面安装包（仅要求浏览器响应式布局，见用户故事 60）。
- 国际化（i18n）：界面固定简体中文，不预留多语言框架。
- 第三方笔记软件导入/导出（Obsidian/Notion/Markdown 双向同步等）。
- 首页额外的可视化区块（趋势折线、学习热力图、四类占比环、问题解决率环等，均已由 `docs/00` 记录评估结论：今后若确有需求，正确做法是另开"数据页"，而不是继续扩容首页）。
- 数据文件分片/分表（按年份等拆分单个大类文件为多文件）——`docs/00` ADR-002 已记录分片是"若单文件体量确实突破实用上限（约 5 万条）时"才重新评估的后续选项，不在本次范围内；即使将来真触发，方案明确是"改一处枚举即可，而不是迁移到数据库"。
- 数据库（SQLite 或任何其他持久化引擎），本次范围确定沿用"每个文件一个 JSON"的第一版决策（ADR-002）。
- 复杂拖拽排序（HTML5 DnD 或第三方拖拽库）——已被 ADR/`docs/01` 明确拒绝，改用 `↑`/`↓` 邻位按钮（用户故事 9）。
- 账号级数据加密（"密码锁"、文件级加密）——数据文件保持为可直接用文本编辑器打开的明文 JSON，是本方案"数据是我的"前提的一部分，明确不做加密。
- **前端测试框架 / 后端单元测试框架**：不引入 Jest/Vitest/JUnit/Mockito；由 seam 设计与 `smoke-test.ps1`（后端）+ 人工 checklist & 全仓库反向搜索（前端）共同承担验证职责。
