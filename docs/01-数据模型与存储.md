## 1.1 文件布局

`data/` 目录下共 5 个数据文件 + 1 个备份子目录：

| 文件 | 内容 | 对应类别 `type` |
|---|---|---|
| `inspirations.json` | 灵感 | `inspiration` |
| `questions.json` | 问题 | `question` |
| `knowledge.json` | 碎片知识 | `knowledge` |
| `todos.json` | 要做的事 | `todo` |
| `wishlist.json` | 心愿单（独立数据域，非记录） | — |
| `.backup/` | 写入前自动快照 | — |

**文件名 ↔ 类别的映射是唯一权威来源**，在 `Category` 枚举中定义（见 02 §2.2），代码中禁止出现字符串硬编码的文件名。

### 1.1.1 每个记录文件的顶层结构

```json
{
  "version": 1,
  "updatedAt": "2026-10-02T14:23:11.482+08:00",
  "records": [ /* Record 对象数组 */ ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | `int` | 数据结构版本号，当前恒为 `1`。为将来的迁移脚本预留判别依据 |
| `updatedAt` | `string` | 本文件最后一次成功写入的时间，ISO-8601 带时区偏移 |
| `records` | `array` | 记录数组，按 `createdAt` 升序追加（不保证有序，读取时排序） |

**为什么要有 `version`**：现在没有用，但一旦字段结构变更（例如把 `status` 从字符串改为对象），没有版本号就只能靠"猜文件长什么样"来兼容旧数据。加这个字段的成本是零，收益是未来可写确定性迁移脚本。

**为什么要有 `updatedAt`**：备份恢复时需要判断哪份快照最新；另外运维排查时能一眼看出数据文件是否被外部工具改动过（外部改动不会更新此字段，是一个有用的信号）。

### 1.1.2 心愿单文件的顶层结构

```json
{
  "version": 1,
  "updatedAt": "2026-10-02T14:23:11.482+08:00",
  "items": [ /* WishItem 对象数组 */ ]
}
```

结构与记录文件一致，仅数组字段名为 `items`。

## 1.2 Record 字段字典

一条记录的完整字段。**所有时间字段统一使用 ISO-8601 带时区偏移格式**（`2026-10-02T14:23:11.482+08:00`），由 `java.time.OffsetDateTime` 序列化。

### 1.2.1 公共字段（四类共有）

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | `string` | 是 | 服务端生成 | UUID v4，创建后不可变。示例：`"3f8a1c2e-9b47-4d11-a6e5-2c7f0b8d4e19"` |
| `type` | `string` | 是 | 由所在文件决定 | 枚举：`inspiration` / `question` / `knowledge` / `todo`。冗余存储（文件名已隐含），用于跨类别操作时自证身份 |
| `title` | `string` | 是 | — | 标题，1~120 字符，首尾空白会被 trim |
| `content` | `string` | 否 | `""` | 正文，Markdown 格式，无长度上限 |
| `tags` | `array<string>` | 否 | `[]` | 标签数组。单个标签 1~24 字符；**存储时按 Unicode 升序去重排序**，避免同一组标签产生多种文件形态 |
| `notes` | `array<Note>` | 否 | `[]` | 追加式笔记，见 §1.3 |
| `status` | `string` | 是 | 见 §1.4 | 状态，合法取值随 `type` 变化 |
| `createdAt` | `string` | 是 | 服务端生成 | 创建时间，不可变 |
| `updatedAt` | `string` | 是 | 服务端生成 | 最后修改时间。**仅当 title/content/tags/status/类别专有字段变化时更新；追加或删除笔记同样更新** |
| `pinned` | `boolean` | 否 | `false` | 置顶标记。列表默认排序中置顶项优先 |

### 1.2.2 类别专有字段

| 字段 | 类型 | 适用类别 | 必填 | 说明 |
|---|---|---|---|---|
| `subject` | `string` | `knowledge` | **是** | 学科。支持 `/` 分层，如 `数学/线性代数`。最多 3 层，每层 1~20 字符 |
| `source` | `string` | `knowledge` `question` | 否 | 来源，如书名章节、课程名、URL。自由文本，≤200 字符 |
| `dueDate` | `string` | `todo` | 否 | 截止日期，**仅日期**格式 `yyyy-MM-dd`（不含时间与时区） |
| `priority` | `string` | `todo` | 否 | `low` / `normal` / `high`，默认 `normal` |
| `doneAt` | `string` | `todo` | 否 | 完成时间。`status` 变为 `done` 时由服务端写入，回退为 `open` 时清空 |

**不适用的类别上，专有字段一律为 `null` 且不写入文件**（Gson 默认不序列化 null）。例如灵感记录中不会出现 `"subject": null`。

## 1.3 Note 结构

```json
{
  "id": "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d",
  "content": "查了一下，这个思路叫 SM-2 算法的简化版",
  "createdAt": "2026-10-03T09:12:44.103+08:00",
  "updatedAt": null
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | `string` | 是 | UUID v4，独立于所属记录的 id |
| `content` | `string` | 是 | 笔记正文，Markdown，1~5000 字符 |
| `createdAt` | `string` | 是 | 创建时间，不可变 |
| `updatedAt` | `string` | 否 | 仅在被编辑过时存在，未编辑则为 `null`（不落盘） |

**追加式语义**：笔记按 `createdAt` 升序在详情页展示，新增追加到末尾。**不允许批量替换整个 `notes` 数组**——API 只提供"新增一条""编辑一条""删除一条"三个动作（见 03 §3.3）。这是为了防止前端误操作把整段历史覆盖掉。

## 1.4 状态（status）取值表

状态是**类别相关**的枚举。校验规则：写入时 `status` 必须属于该 `type` 的合法集合，否则返回 `400 invalid_status`。

| 类别 | 合法状态 | 创建时默认 | 语义 |
|---|---|---|---|
| `inspiration` 灵感 | `active` / `archived` | `active` | `active` 在池中；`archived` 已被验证或已放弃，不再出现在随机回顾 |
| `question` 问题 | `open` / `resolved` | `open` | `resolved` 表示已弄懂，详情页应引导补充答案到正文或笔记 |
| `knowledge` 碎片知识 | `learning` / `mastered` | `learning` | `mastered` 表示已掌握；**仍参与随机回顾**（复习语义） |
| `todo` 要做的事 | `open` / `done` / `cancelled` | `open` | `done` 完成；`cancelled` 取消（不计入完成率分母，见下） |

### 1.4.1 「完成/未完成」的统计口径（重要）

首页饼图只有两片，但 `todo` 有三个状态，必须明确归口：

- **`done`（已完成）** → 饼图的 `done` 片
- **`open`（未完成）** → 饼图的 `open` 片
- **`cancelled`（已取消）** → **不计入饼图**

**理由**：取消的事既不是完成也不是待办，把它算进"未完成"会虚增待办压力，让完成率失真。饼图反映的是"我承诺要做的事里做完了多少"，取消的承诺不应参与。

完成率计算式：

```
completionRate = done / (done + open)      当 done + open == 0 时，completionRate = null
```

**`null` 而非 `0`**：一条待办都没有时，完成率是"无定义"而不是"0%"。前端遇 `null` 应显示「暂无待办」而非画一个 0% 的空环——后者会让人误以为自己有大量未完成事项。

`cancelled` 的数量在 `/api/stats/overview` 中以独立字段 `todoCancelled` 返回，前端可在饼图下方以小字显示「另有 N 项已取消」，保证信息不丢失。

## 1.5 心愿单（WishItem）字段字典

```json
{
  "id": "e07a4c95-1b38-42f6-9d04-c8b51e7f2a30",
  "name": "HHKB Professional HYBRID Type-S",
  "amountCents": 238800,
  "note": "等双11，看看能不能到 2000 以内",
  "purchased": false,
  "purchasedAt": null,
  "createdAt": "2026-09-15T21:08:44.120+08:00",
  "updatedAt": "2026-09-15T21:08:44.120+08:00",
  "sortIndex": 0
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | `string` | 是 | 服务端生成 | UUID v4 |
| `name` | `string` | 是 | — | 想要的东西，1~120 字符 |
| `amountCents` | `long` | 是 | — | 金额，**单位：分**。取值 `0 ~ 999_999_999_99`（即最多 9.99 亿元）。不接受负数 |
| `note` | `string` | 否 | `""` | 备注，如"等打折""已下单在途"，≤500 字符 |
| `purchased` | `boolean` | 是 | `false` | 是否已买。为真时 UI 上金额加删除线 |
| `purchasedAt` | `string` | 否 | `null` | 购买时间。`purchased` 转真时写入，转假时清空 |
| `createdAt` | `string` | 是 | 服务端生成 | 加入心愿单的时间 |
| `updatedAt` | `string` | 是 | 服务端生成 | 最后修改时间 |
| `sortIndex` | `int` | 是 | `0` | 手动排序序号，升序展示。新建时取 `max(sortIndex)+1` |

### 1.5.1 三项汇总的计算规则

由 `WishlistService.summary()` 计算，**前端不得自行累加**（避免口径漂移）：

```java
totalWish  = Σ amountCents                        // 所有条目，不论是否已购
spent      = Σ amountCents where purchased == true
remaining  = totalWish - spent
```

三个值均以**分**为单位在 API 中传输，前端格式化为元展示（`amountCents / 100`，保留两位小数，千分位分隔）。

**注意 `totalWish` 包含已购条目**——这是刻意的。需求原文是"累计总心愿钱数、已经花掉钱数、还差的钱数"，三者构成 `总 = 已花 + 还差` 的恒等式。若 `totalWish` 排除已购项，恒等式不成立，"还差"就失去了参照。

**溢出防护**：`amountCents` 上限设为 `999_999_999_99`（约 10 亿元），`long` 上限约 `9.22 × 10^18`，即使有 900 万条顶格条目也不会溢出。校验时超限直接拒绝，而非静默截断。

### 1.5.2 为什么用整数分

见 [00 §ADR-005](./00-总览与技术选型.md#adr-005--心愿单条目永不删除仅切换-purchased-标记)。要点重述：`double` 累加金额会产生浮点误差（`0.1 + 0.2 = 0.30000000000000004`），导致"还差的钱数"出现小数尾差。用 `long` 存分可彻底规避，且比 `BigDecimal` 少写大量样板代码。

**前端展示的唯一正确做法**：

```js
const yuan = (cents) => (cents / 100).toFixed(2);   // 仅用于展示
```

**禁止**在前端对元做加减后再转回分——所有算术都在分的整数域完成。

## 1.6 内存索引策略

### 1.6.1 为什么需要索引

JSON 文件无索引能力，任何查询都是全表扫描。若每次 HTTP 请求都重新读文件 + 解析，在数据量增长后延迟会线性上升，且磁盘 I/O 无谓重复。

### 1.6.2 策略：启动全量载入 + 内存为查询源 + 写时回刷

```
启动时：
  for each of 5 files:
      read → parse → 放入 ConcurrentHashMap<String, Record>（key = id）
      同时维护 List<Record> 作为遍历序（保持文件中的原始顺序）

查询时（GET）：
  只读内存，不碰磁盘

写入时（POST/PATCH/DELETE）：
  1. 取该文件的写锁
  2. 修改内存中的对象
  3. 序列化整个文件内容 → 原子写盘（见 §1.7）
  4. 释放写锁
```

**数据结构**：

```java
// 每个类别一份
private final Map<String, Record> byId;      // id → Record，O(1) 定位
private final List<Record> ordered;          // 保持文件顺序，用于序列化回写
private final ReentrantReadWriteLock lock;   // 每文件独立锁，互不阻塞
```

**`byId` 与 `ordered` 必须同步维护**——这是最容易出 bug 的地方。规则：所有增删改都通过 `JsonStore` 的私有方法完成，这两个容器只在 `JsonStore` 内部被触碰，任何外部代码拿到的都是**不可变副本**。

### 1.6.3 数据量与性能预估

| 记录条数（单文件） | 文件大小估算 | 全量重写耗时 | 内存查询耗时 |
|---|---|---|---|
| 100 | ~150 KB | < 5 ms | < 1 ms |
| 1,000 | ~1.5 MB | ~20 ms | < 2 ms |
| 10,000 | ~15 MB | ~150 ms | ~10 ms |

估算依据：单条记录（含 300 字正文）序列化后约 1.5 KB；SSD 顺序写吞吐约 100 MB/s 量级。

**结论**：单用户学习记录场景下，1 万条以内完全无压力。写入耗时（150 ms）在 1 万条量级仍可接受，因为写入是低频动作（人工录入）。

**性能红线与应对**：若单文件超过 5 万条，全量重写会退化到秒级。此时的正确应对是**按年份分片**（`knowledge-2026.json`），而不是引入数据库——分片保持了"人工可编辑"的核心优势。本项目不实现分片，但 `JsonStore` 的文件路径解析集中在 `Category` 枚举一处，将来加分片只需改这一处。

## 1.7 原子写入与备份

这是纯 JSON 存储方案**最关键**的一环。ADR-002 已识别出"写入中断可能损坏整类数据"的风险，此处给出完整对策。

### 1.7.1 风险场景

直接 `Files.write(path, bytes)` 不是原子的。若在写入过程中发生以下情况：

- JVM 崩溃 / 被 `kill`
- 系统断电
- 磁盘写满

文件会处于**部分写入**状态——可能是空文件，可能是被截断的 JSON。整个类别的数据全部无法解析，等同于丢失。

### 1.7.2 对策：临时文件 + 原子 move

```
写入流程（持有该文件写锁）：
  1. 备份：把当前 data/xxx.json 复制到 data/.backup/xxx.<timestamp>.json
  2. 序列化：Gson 生成完整 JSON 字节数组（在内存中完成，失败则中止，不动磁盘）
  3. 写临时文件：data/.xxx.json.tmp  ← 与目标同目录，保证同一文件系统
  4. 强制刷盘：对临时文件 channel 调 force(true)，确保数据落到物理介质
  5. 原子替换：Files.move(tmp, target, ATOMIC_MOVE, REPLACE_EXISTING)
  6. 清理：若 move 失败，删除临时文件
```

**关键点解释**：

- **第 3 步必须同目录**：`ATOMIC_MOVE` 依赖操作系统的 rename 语义，跨文件系统（如临时文件放 `C:\Temp`，目标在 `D:\`）会退化为"复制+删除"，失去原子性。
- **第 4 步的 `force(true)` 不可省略**：操作系统的 rename 只保证元数据原子性，不保证文件内容已落盘。跳过这步，断电后可能得到一个"长度正确但内容全是零"的文件。
- **第 2 步在内存中完成序列化**：如果对象图有问题导致 Gson 抛异常，此时磁盘上的原文件还完好无损。先算好再落盘，是"要么全成功要么不动"的基础。

### 1.7.3 备份策略

| 项 | 规则 |
|---|---|
| 触发时机 | 每次写操作（POST/PATCH/DELETE）前，且仅当目标文件当前存在且非空 |
| 命名 | `<原文件名去扩展>.<yyyyMMdd-HHmmss-SSS>.json`，例：`todos.20261002-142311-482.json` |
| 保留数量 | 每个数据文件最多保留 **50** 份，超出按时间戳删除最旧的 |
| 存放位置 | `data/.backup/`（点号开头，前端静态服务不会暴露此目录） |
| 批量操作 | 单次请求内的多次写入共用一份备份（避免一次 PATCH 产生多份冗余快照） |

**为什么是 50 份**：单文件 1.5 MB × 50 = 75 MB，占用可忽略；同时覆盖了"最近几十次修改"，足够应对"刚才误删了一条，想退回去"这种最常见的恢复需求。

### 1.7.4 锁策略

```java
每个数据文件 → 一把独立的 ReentrantReadWriteLock

读操作（GET）  → readLock()   多个读并发
写操作（POST/PATCH/DELETE） → writeLock()  独占
```

**分文件锁而非全局锁**：编辑一条灵感和勾选一个心愿条目互不阻塞。这对单用户场景收益有限，但实现复杂度相同，没有理由做成全局锁。

**读写锁而非 `synchronized`**：查询是高频操作（首页一次加载触发 3 个请求），读锁允许并发，避免列表查询被一个正在进行的写入长时间阻塞。

**锁的持有范围必须包含整个"改内存 → 写盘"过程**。若只锁内存修改而不锁写盘，两个并发写可能各自改了内存，然后交叉写盘，导致后写的覆盖先写的。

### 1.7.5 启动时的损坏恢复

启动加载时若某文件解析失败，**不得直接崩溃退出**（那会让用户连数据都看不到）。处理流程：

```
尝试解析 data/xxx.json
  ├─ 成功 → 正常载入
  └─ 失败 → 记录错误，按序尝试 .backup/ 中该文件的快照（从最新往旧）
              ├─ 某份快照解析成功 → 载入它，并在控制台显著警告：
              │     "⚠ xxx.json 已损坏，已从备份 <文件名> 恢复。
              │      损坏文件已保留为 xxx.json.corrupt，请人工检查。"
              │   同时把损坏的原文件重命名为 xxx.json.corrupt（不删除，供排查）
              └─ 所有快照均失败 → 该类别载入为空列表，控制台警告，服务照常启动
                  （其余类别不受影响，用户仍可访问）
```

**文件不存在**（首次运行）与**文件损坏**是两种情况：前者静默创建空结构，后者走上述恢复流程。

## 1.8 数据一致性的边界

纯文件存储没有事务。必须明确哪些操作是安全的，哪些需要设计规避。

| 操作 | 涉及文件数 | 原子性 | 说明 |
|---|---|---|---|
| 新建/编辑/删除记录 | 1 | ✅ | 单文件写，原子 |
| 追加/编辑/删除笔记 | 1 | ✅ | 笔记内嵌于记录，同文件 |
| 修改心愿条目 | 1 | ✅ | 单文件写 |
| **跨类别移动记录** | 2 | ⚠️ | 见下 |

### 1.8.1 唯一的跨文件操作：变更类别

用户可能想把一条「问题」改成「碎片知识」（弄懂了，沉淀为知识）。这需要从 `questions.json` 删除、往 `knowledge.json` 添加。

**风险**：若删除成功但添加失败，记录丢失。

**对策：先加后删**

```
1. 校验目标类别的必填字段（如转 knowledge 必须有 subject）
2. 取【两个】文件的写锁（按 Category 枚举序固定加锁顺序，避免死锁）
3. 先在目标文件中插入新记录（保留原 id，改 type 与 updatedAt）
4. 原子写目标文件 → 成功
5. 再从源文件移除 → 原子写源文件
6. 释放两把锁
```

**为什么"先加后删"而非"先删后加"**：两种顺序都可能中断，但后果不同。

- 先删后加中断 → 记录**只存在于备份中**，用户视角是数据丢失。
- 先加后删中断 → 记录**同时存在于两个文件**，用户视角是多了一条重复项。

后者可检测、可修复（启动时扫描全局重复 id 并告警），前者不可见。因此选后者。

**固定加锁顺序**：始终按 `Category` 枚举的声明序获取锁（`inspiration` < `question` < `knowledge` < `todo`）。若两个请求同时做 A→B 和 B→A 的移动，无序加锁会死锁；固定顺序则不会。

**启动时重复 id 检测**：加载完 5 个文件后，检查是否存在跨文件重复的 `id`。若有，控制台告警并列出，保留 `updatedAt` 较新的那份，另一份标记为 `.corrupt-duplicate` 供人工处理。这是"先加后删"策略的兜底。

## 1.9 校验规则汇总

所有校验在 `RecordService` / `WishlistService` 层执行，`JsonStore` 不做业务校验。违反任一条返回 `400`，错误码见 [03 §3.9](./03-API契约.md#39-错误码表)。

### 记录

| 字段 | 规则 | 错误码 |
|---|---|---|
| `type` | 必填，须为四个合法值之一 | `invalid_type` |
| `title` | 必填，trim 后长度 1~120 | `invalid_title` |
| `content` | 可选，长度 ≤ 100_000 | `invalid_content` |
| `tags` | 可选，数组长度 ≤ 20；单个标签 trim 后 1~24 字符，不含 `/` | `invalid_tags` |
| `status` | 必填，须属于该 `type` 的合法集合（§1.4） | `invalid_status` |
| `subject` | `knowledge` 时**必填**；1~3 层，每层 trim 后 1~20 字符，以 `/` 分隔 | `invalid_subject` |
| `source` | 可选，长度 ≤ 200 | `invalid_source` |
| `dueDate` | `todo` 时可选；格式 `yyyy-MM-dd`，须为可解析的真实日期 | `invalid_due_date` |
| `priority` | `todo` 时可选；`low`/`normal`/`high` | `invalid_priority` |
| `pinned` | 可选布尔 | `invalid_pinned` |
| 专有字段越界 | 不适用的类别上传了专有字段 → **忽略**（不报错，宽容处理） | — |

**为什么专有字段越界选择忽略而非报错**：前端可能因为类别切换而残留字段（如把灵感改成待办时表单里还有 `subject`）。报错会迫使前端精确清理每个字段，而忽略这些字段对数据无害（不会被序列化落盘）。宽容读取、严格写出。

### 笔记

| 字段 | 规则 | 错误码 |
|---|---|---|
| `content` | 必填，trim 后 1~5000 字符 | `invalid_note` |
| `noteId` | 路径参数，须存在于该记录的 `notes` 中 | `note_not_found` |

### 心愿条目

| 字段 | 规则 | 错误码 |
|---|---|---|
| `name` | 必填，trim 后 1~120 字符 | `invalid_wish_name` |
| `amountCents` | 必填，整数，`0 ~ 999_999_999_99` | `invalid_amount` |
| `note` | 可选，长度 ≤ 500 | `invalid_wish_note` |
| `purchased` | 可选布尔 | `invalid_purchased` |
| `sortIndex` | 可选整数，`0 ~ 1_000_000` | `invalid_sort_index` |

### 查询参数（GET）

查询参数校验采取**宽容策略**：非法值不报错，而是回退到默认值。理由是查询失败对用户毫无价值，返回一个合理的默认结果集比返回 400 更有用。

| 参数 | 非法时的行为 |
|---|---|
| `page` ≤ 0 或非数字 | 回退为 `1` |
| `size` 超出 1~200 | 夹紧到边界（`0` → `1`，`500` → `200`） |
| `sort` 非法值 | 回退为 `updatedAt` |
| `order` 非 `asc`/`desc` | 回退为 `desc` |
| `type` 非法值 | **例外**：返回 `400 invalid_type`（因为它决定了读哪个文件，无法回退） |

放置于 `docs/schema/record.schema.json`。作用有二：① 人工编辑数据文件时，VS Code 等编辑器可据此给出补全和错误提示；② 将来若写迁移脚本，可作为校验依据。**后端运行时不加载此 Schema**（校验由 §1.9 的 Java 代码执行），避免引入 Schema 校验库依赖。

    "tags":      { "type": "array", "maxItems": 20,
                   "items": { "type": "string", "minLength": 1, "maxLength": 24 } },

## 1.11 初始种子文件

首次运行时，若某数据文件不存在，`JsonStore` 自动创建如下内容（记录文件示例）：

```json
{
  "version": 1,
  "updatedAt": "2026-10-02T14:23:11.482+08:00",
  "records": []
}
```

心愿单文件同理，数组字段为 `items`。

**不预置任何示例数据**。理由：示例数据会污染统计（首页饼图一开始就有数字）、混入标签自动补全、并需要用户手动删除。空数据状态下，前端应显示**空状态引导**（见 04 §4.7），提示"还没有记录，点这里新建第一条"。
