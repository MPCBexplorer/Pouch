## 0.1 项目定位

**Pouch** 是一个**单用户、本地运行**的学习记录看板。

它解决的具体问题是：学习过程中随手记下的东西（灵感、问题、碎片知识、要做的事）散落在各处，缺少一个统一的落点，既不方便回看，也不会主动"跳出来"提醒你。

因此产品有两个核心动作：

1. **存** —— 以 JSON 文件形式结构化落盘，人工可直接读写。
2. **看** —— 本地 Web 服务呈现，首页做聚合看板（统计、心愿单进度、随机回顾），其余页面做分类浏览、筛选、详情编辑。

**关键特征**：

- 单用户，无鉴权，无多租户。
- 数据完全在本地，纯 JSON 文件，不使用数据库。
- 本地服务器（`127.0.0.1`）访问，不对外暴露。
- 数据文件应可被 Git 版本管理，也应可被文本编辑器直接修改。

## 0.2 功能范围

### 0.2.1 首页 · 数据看板（`index.html`）

六个区块。桌面端 2~3 列栅格，窄屏单列堆叠；A 横跨整行，B/E/C 一行，D/F 一行：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| **A. 总量统计条** | 四个类别各自的记录总数，四个可点击卡片，点击跳转到对应列表页 | `GET /api/stats/overview` |
| **B. 完成/未完成环形图** | 「要做的事」的 `done` / `open` 占比环形图，中心显示完成率百分比；下方小字「另有 N 项已取消」 | `GET /api/stats/overview` |
| **C. 心愿单概览** | **只有可视化汇总，不列条目**：总额 / 已花 / 还差三个数字 + 一根进度条（已花占总额比例）+「N 项已实现 / 共 M 项」；「查看全部」按钮跳转 `wishlist.html` | `GET /api/wishlist`（只取 `summary`，忽略 `items`） |
| **D. 随机回顾** | **一个区块，顶部 tab 切换 `灵感` / `知识点`**。显示标题 + 内容摘要 +「换一条」按钮；点击卡片进详情。知识点 tab 额外显示学科徽标 | `GET /api/stats/random?type=inspiration\|knowledge` |
| **E. 碎片知识构成环** | 一个环形图，**滑块切换 `按学科` / `按标签`** 两种维度。两者形态一致（均为环形图），仅数据源与配色不同 | `GET /api/meta/subjects`、`GET /api/meta/tags?type=knowledge` |
| **F. 陈旧提醒** | 长期未被推进的记录 Top N，按停滞天数降序；每条显示标题、类别徽标、状态、停滞天数，点击进详情。附各类别陈旧条数分布 | `GET /api/stats/stale` |

> **区块 D 的设计意图**：这是本产品区别于普通笔记应用的地方——它让沉下去的记录**主动浮上来**。抽取出灵感与知识点共用一套渲染逻辑，仅 `type` 不同，因此合并为一个区块 + tab（ADR-011）。抽取应在前端做"不重复连续抽取"（连续点「换一条」不出现同一条，直到遍历完一轮），**且两个 tab 各自维护独立的已看列表**。

> **区块 C 为什么不在首页列条目**：心愿单条目会持续增长，列表越长首页越慢，且"逐个勾选购买"是一个需要专注的操作，与首页"一眼看完"的定位冲突。首页只保留最有信息量的三个数字和一根进度条——**看到"还差 ¥4,776"这个事实**比看到具体想买了什么更能影响决策。条目管理移到专页 `wishlist.html`（§0.2.4）。

> **区块 F 的设计意图**：B 和 E 都是"状态快照"，F 是**唯一能促使行动的看板**——它指出你在忽视什么。一个学习系统最容易失败的方式不是记录太少，而是记了就沉底。判定规则与阈值见 ADR-009。

### 0.2.2 列表页 · 分类浏览（`list.html`）

- 左侧固定导航：四个类别 + 心愿单，显示各类别计数徽标。
- 顶部筛选栏，**按当前类别动态变化**：
  - 通用：关键词搜索（标题 + 正文）、标签多选、状态、排序（时间/更新时间/标题）、每页条数
  - 碎片知识额外：**学科**下拉筛选（支持按 `/` 分层，如 `数学/线性代数`，UI 按一级分组）
  - 要做的事额外：截止日期范围
- 主体默认**列表视图**：每行显示标题、摘要（正文前两行，去 Markdown 标记）、标签、状态徽标、相对时间。
- 行点击进入详情页。
- 右上角「+ 新建」按钮，弹出模态框快速录入。

### 0.2.3 详情页 · 查看与编辑（`detail.html`）

- 正文以 Markdown 渲染（只读态）；「编辑」切换到 textarea，保存后重新渲染。
- **笔记区**：可追加多条带时间戳的笔记，每条可单独编辑/删除。这是"事后补充想法"的落点，不覆盖原正文。
- **标签区**：可增删标签，输入时给出已有标签的自动补全。
- 元信息面板：创建时间、更新时间、状态、（碎片知识）学科。
- 状态切换按钮随类别变化：`要做的事` → 标记完成；`问题` → 标记已解决；`碎片知识` → 标记已掌握；`灵感` → 归档。

### 0.2.4 心愿单页 · 条目管理（`wishlist.html`）

承接首页区块 C 的「查看全部」。这是心愿单**唯一的完整管理界面**：

- **条目列表**：名称 + 右侧金额；已购条目金额加删除线并显示实现日期，但**条目不消失**（ADR-005）。
- **勾选已购**：每条一个开关，切换即 `PATCH`，页面顶部三个数字与进度条实时联动。
- **顶部汇总区**：总额 / 已花 / 还差，加一根进度条——与首页区块 C 同源同算法，**不得各自实现一遍**。
- **快速新增**：名称 + 金额（元，前端换算为分），无需跳转。
- **排序**：默认**按创建时间**（先加的在前）。每条右侧提供 `↑` `↓` 两个按钮交换相邻位置，交换即持久化为新的 `sortIndex`。**不做拖拽**（HTML5 DnD 代码量大且手机上不可用，收益不抵成本）。
- **备注**：每条可写一句备注（如"等双11，看看能不能到 2000 以内"），列表中以小字显示。

> **"默认按创建时间"与 `sortIndex` 如何共存**：新建条目时 `sortIndex` 取「当前最大值 + 1」，因此**未经手动调整时，`sortIndex` 升序天然等价于创建时间升序**——两套顺序在初始状态是同一个，不存在冲突。用户按 `↑` `↓` 之后，`sortIndex` 才偏离创建时间顺序，此时以 `sortIndex` 为准。后端排序规则始终是 `sortIndex` 升序 → `createdAt` 升序 → `id`（三级，见 03 §3.5），**不需要**为此新增任何字段或端点。
>
> **`↑` `↓` 的实现要点**：交换两条记录的 `sortIndex` 即可，是**两次独立 `PATCH`**，不需要批量排序接口。若其中一次失败，页面重新拉取 `wishlist` 恢复到服务端真实状态，不做乐观回滚——本地服务下两次请求都成功的概率极高，为小概率情况引入事务语义不值得。

> **删除条目的处理**：提供删除，但需二次确认，并明确提示"删除后可从 `data/.backup/` 恢复"。ADR-005 的"永不删除"指的是**买到了不删条目**（要保留"已实现"的历史），不是禁止用户主动清理误录。

### 0.2.5 明确的非目标

以下**不在**本项目范围内，写入文档以免开发中范围蔓延：

- ❌ 用户注册、登录、鉴权、权限
- ❌ 多设备同步、云端存储、协同编辑
- ❌ 全文检索引擎（Lucene/ES 级别）——搜索是内存遍历 + 子串匹配
- ❌ 附件/图片上传与存储（正文可引用本地已有图片的相对路径，但不做上传接口）
- ❌ 移动端 App、PWA 离线（仅要求响应式布局在手机浏览器可用）
- ❌ 国际化（界面固定简体中文）
- ❌ 导入导出为其他笔记软件格式

**分层职责边界**（写代码时严格遵守，避免逻辑下沉或上浮）：

- **Handler 层**：只做 HTTP 语义——解析参数、校验入参、调用 Service/Store、组装响应状态码与 JSON。**不写业务规则**。
- **Store 层**：只管文件读写、锁、原子性、备份、内存索引维护。**不解析 HTTP，不校验业务字段**。
- **前端 `api.js`**：唯一发起 `fetch` 的地方。页面代码只调用 `api.xxx()`，不直接拼 URL。
- **前端页面 JS**：只做渲染与交互，不重复实现后端已有的聚合逻辑（统计一律走 `/api/stats/*`）。

## 0.5 架构决策记录（ADR）

### ADR-001 · 后端语言选 Java 21，放弃 Zig

**背景**：最初设想用 Zig，退路 Java。

**决策**：使用 **Java 21**（本机已安装 `C:\Program Files\Microsoft\jdk-21.0.8.9-hotspot`）。

**理由**：

1. **Zig 未安装**，且其生态对本项目不友好：`std.http.Server` 可用但无路由/中间件生态，JSON 需手写或用不成熟的第三方库；更关键的是 Zig 在 0.11 → 0.13 → 0.14 之间多次破坏性变更 API，学习项目会被语言本身的动荡拖住。
2. Java 21 的 `com.sun.net.httpserver.HttpServer` 是 **JDK 自带**（`jdk.httpserver` 模块），零依赖即可提供 HTTP 服务能力，完全够本项目使用。
3. Java 21 的 `switch` 模式匹配、`record`、文本块（text block）、`var` 都能显著减少样板代码，写起来并不笨重。

**代价与应对**：

- 本机**没有 Maven / Gradle**（已核查）。→ 不使用构建工具，改用 `javac` + `java -cp` 直接编译运行，由 `build.ps1` / `start.ps1` 封装。第三方 jar 手动放入 `server/lib/`。
- Java 21 的单文件源码运行模式（`java Foo.java`，JEP 330）**只支持单个文件**；多文件源码启动是 Java 22 的 JEP 458。→ 本项目多文件，必须走 `javac` 编译到 `server/out/` 再运行。

**替代方案**：Node.js（本机已装，生态最省事，但偏离原技术偏好，且引入 `node_modules` 后"纯本地零依赖"的优势消失）。

### ADR-002 · 数据按大类分 JSON 文件，不使用数据库

**决策**：四个记录类别 + 心愿单，各一个 JSON 文件，共 5 个文件，位于 `data/`。

**理由**：符合"我会把这些记录做成 json 格式"的原始设想；人工可用编辑器直接改；可被 Git 追踪，天然有版本历史。

**代价（必须正视）**：

| 代价 | 应对方案 | 详见 |
|---|---|---|
| 每次写入需整文件重写 | 单用户场景下量级可接受（1 万条约 10~20 MB，重写耗时毫秒级） | 01 §1.6 |
| 写入中断可能损坏整类数据 | **临时文件 + 原子 move** 写入；写前自动备份 | 01 §1.7 |
| 无索引，查询是全表扫描 | 启动时载入内存，查询在内存做；文件仅作持久化 | 02 §2.5 |
| 并发写冲突 | 每文件一把 `ReentrantReadWriteLock` | 01 §1.7 |
| 无事务，跨文件操作不原子 | 设计上避免跨文件写；唯一例外见 01 §1.8 | 01 §1.8 |

**明确排除**：SQLite。虽然聚合查询能力更强，但引入 JDBC 驱动依赖，且失去"人工可直接编辑 JSON"这一核心优势。

### ADR-003 · 统一记录模型（单表继承），而非四类各自建模

**决策**：`灵感 / 问题 / 碎片知识 / 要做的事` 共用同一个 `Record` 结构，类别由 `type` 字段区分，类别专有字段（如 `subject`、`dueDate`）在不适用的类别上为 `null`。

**理由**：

1. 四类记录的公共部分（标题、正文、标签、笔记、时间戳、状态）占绝大比重，拆开会产生四套高度重复的 CRUD 代码。
2. 列表页、详情页、搜索、标签系统可以对四类完全复用同一套前后端逻辑，只靠 `type` 参数分流。
3. 未来新增类别（如"读书笔记"）只需在 `Category` 枚举加一项，无需新建文件结构与端点。

**代价**：JSON 中存在值为 `null` 的字段。→ Gson **默认就不序列化 null**，因此不调用 `serializeNulls()` 即可让落盘文件保持干净（详见 02 §2.3 的配置说明）。

**校验责任**：Store 层不校验业务字段，由 `RecordService` 按 `type` 做**类别相关的必填校验**（如 `knowledge` 必须有 `subject`）。见 02 §2.6。

### ADR-004 · 完成/未完成饼图的数据源限定为「要做的事」

**背景**：需求原文是"完成/未完成饼图"，未说明统计范围。

**决策**：饼图数据源为 `type=todo` 的记录，按 `status` 分为 `done` / `open` 两片。

**理由**：四个类别中，只有「要做的事」的"完成"语义是无歧义的。灵感没有"完成"，碎片知识的"掌握"和问题的"解决"是不同性质的状态，混在一个饼图里会失去意义。

**扩展性**：`/api/stats/overview` 的响应中**同时返回四类各自的 status 分布**，前端只取 todo 那一份画饼图。

> **已评估并否决的扩展**：曾考虑用同样的数据加"问题解决率"环和"知识掌握度"环。否决理由——这两个指标是**状态快照而非需要盯的趋势**，问题解决率高低本身不驱动任何行动，知识掌握度更是主观标记（自己点的"已掌握"不构成可信统计）。做成环图只会占用首屏。数据仍然返回（成本为零），但**前端不渲染**。见 ADR-008。

### ADR-005 · 心愿单条目永不删除，仅切换 `purchased` 标记

**背景**：需求原文明确"如果买了，就划掉金额（条目不删除）"。

**决策**：

- 购买 = `PATCH` 将 `purchased` 置 `true` 并记录 `purchasedAt`；取消购买 = 置回 `false` 并清空 `purchasedAt`。
- 三项汇总由后端计算，前端不重复计算：
  - `totalWish`（总心愿钱数）= 所有条目 `amount` 之和
  - `spent`（已花掉钱数）= `purchased == true` 的条目 `amount` 之和
  - `remaining`（还差的钱数）= `totalWish - spent`
- 金额一律用**整数分（`long`，字段名 `amountCents`）**存储与计算，仅在展示层格式化为元。

**为什么用分而不用 double**：`0.1 + 0.2 != 0.3` 是浮点数基本性质，累加金额会产生分位误差，导致"还差的钱数"出现 `1234.5600000000002` 这类结果。用 `long` 存分可完全避免，且 Java 端无需引入 `BigDecimal` 的样板代码。

**保留 `DELETE` 端点**：用于误录入的清理，但 UI 上入口弱化（详情页底部小字链接 + 二次确认），避免误删破坏"账本"的历史完整性。

### ADR-006 · 前端使用原生 HTML/CSS/JS，无构建步骤

**决策**：不引入 Vue/React/Vite，直接由 Java 后端托管 `web/` 静态目录。

**理由**：改完刷新即生效，无需 `npm run build` 等待；没有 `node_modules`；三个页面的复杂度远未达到需要组件框架的程度。

**视觉质量的保证手段**（回应"要保证好的视觉效果"）：无框架不等于简陋。本项目通过以下方式保证观感——

1. **设计 Token 集中化**：所有颜色、间距、圆角、阴影、字号定义在 `css/tokens.css` 的 CSS 自定义属性中，任何页面不得写死数值。
2. **明暗双主题**：Token 分两套，通过 `[data-theme]` 切换，跟随系统偏好并支持手动覆盖。
3. **一致的组件语汇**：卡片、徽标、按钮、输入框、模态框在 `base.css` 中定义为可复用 class，三个页面共用。
4. **克制的动效**：统一的 `--dur-fast/--dur-base` 与 `--ease-out`，hover 抬升、状态切换过渡，但不做花哨动画。
5. **三个本地化第三方库**：Chart.js（环形图）、marked（Markdown 解析）、DOMPurify（HTML 净化）。均 vendor 到 `web/vendor/`，不走 CDN，保证离线可用。其中 DOMPurify 不是可选项——marked 不做任何过滤，正文中粘贴的网络内容可能携带脚本，必须净化后才能插入 DOM（见 04 §4.9.1）。

**代价**：无组件复用机制，列表项渲染等需要手写 DOM 构造。→ 集中在 `js/dom.js` 提供 `el()` / `frag()` 辅助函数，避免字符串拼接 HTML 带来的 XSS 风险（见 04 §4.9）。

### ADR-007 · 删除采用硬删除 + 自动备份快照

**决策**：`DELETE` 直接从 JSON 数组移除该记录，写盘前自动生成备份快照。

**理由**：软删除（`deleted: true`）会让每个查询都带上过滤条件，且列表计数、统计口径都要额外处理，复杂度不值得。备份快照已能提供恢复能力。

**恢复方式**：从 `data/.backup/` 找到对应时间点的文件，覆盖回 `data/`。文档 05 §5.6 给出恢复步骤。

### ADR-008 · 新增看板不进 `stats/overview`，改开独立端点

**背景**：扩充首页看板（碎片知识构成环、陈旧提醒）时需要新的聚合数据。有两个选择：塞进现有 `stats/overview` 的响应，或新开端点。

**决策**：新开 `GET /api/stats/stale`（陈旧提醒），构成环**复用现有** `meta/subjects` 与 `meta/tags`（后者加 `?type=` 参数）。**`stats/overview` 的响应结构一个字段都不加。**

**理由**：

1. **向后兼容**。`overview` 的字段、`StatsService` 的实现、`index.js` 的 `renderCompletion` 在 02/03/04 三份文档里已经写定且互相引用。往 `overview` 里加字段意味着三份文档同时改，且已实现的代码全部要动。
2. **失败隔离**。陈旧提醒涉及按时间排序，是全库扫描；构成环只读聚合结果。把它们和 `overview` 绑在一起，任一环节变慢都会拖垮首屏最关键的完成率图。分开后各区块**并行请求、独立降级**——某个端点失败只让对应区块显示占位，其余照常渲染（04 §4.6.4 的 `Promise.allSettled` 策略）。
3. **构成环其实不需要新端点**。`meta/subjects` 本来就只统计 `knowledge` 且已带 `ownCount`/`count`；`meta/tags` 只需加一个可选 `type` 过滤参数——这同时让列表页的标签筛选器能按类别收窄，是一个通用增强，不是为环图开的特例。

**代价**：首页并发请求从 3 个增至 5~6 个（`health` `overview` `wishlist` `stale` + 构成环的 `subjects`，切到标签维度时再加 `tags`）。本地回环，每个都是毫秒级，可接受。**构成环的 `tags` 请求应懒加载**——滑块切到「按标签」时才发，不要在首屏就请求两个维度的数据。

**明确不做**：四类占比环（与 A 区块四张计数卡片信息重复）、增长趋势折线、学习热力图、笔记覆盖率。前两类需要时间分桶聚合，收益不抵复杂度；占比环是纯冗余。若将来确实想看趋势，正确做法是新建 `stats.html` 承载，而不是继续堆首页——见 ADR-010。

### ADR-009 · 陈旧提醒的判定规则

**背景**：区块 F 要"提醒长期没推进的记录"。但"陈旧"必须精确定义，否则实现时会拍脑袋，且不同类别的语义差别很大。

**决策**：`idleDays` = 距今未推进的天数，**推进时间直接取 `updatedAt`**。参与范围与阈值按类别区分：

| 类别 | 参与条件 | 默认阈值 | 理由 |
|---|---|---|---|
| `question` | `status = open` | **30 天** | 未解决的问题最容易被遗忘，且遗忘代价最高——这正是本看板最该提醒的东西 |
| `todo` | `status = open` 且**无 `dueDate`** | **21 天** | 有截止日的待办由 `dueDate` 自己驱动提醒，不该混进陈旧列表；无期限的才会无限期沉底 |
| `inspiration` | `status = active` | **60 天** | 灵感需要酝酿期，过早提醒等于噪音 |
| `knowledge` | **不参与** | — | 知识点不存在"推进"，只有"是否复习"。复习已由区块 D 的随机回顾承担，再进陈旧列表是功能重复 |

**为什么 `updatedAt` 足够，不需要额外算笔记时间**：01 §1.2 已规定 `updatedAt` 在 `title`/`content`/`tags`/`status`/类别专有字段变化时更新，**追加或删除笔记同样更新**。因此它已经准确表示"最后被碰过是什么时候"，无需再遍历 `notes[]` 取最大时间戳——那样只会增加一次无谓的全量扫描。

> 这是一个**跨文档依赖**：陈旧提醒的正确性建立在"`updatedAt` 随笔记变动"这条既有规则上。若将来修改 01 §1.2 让笔记不再触碰 `updatedAt`，必须同步改本 ADR，否则"在详情页补了一条笔记却没被顶出陈旧列表"就会成为 bug。

**由此得到的用户可感知行为**：在详情页随手改一个字、或补一条笔记，就能把这条记录从陈旧列表里顶掉。这符合直觉——你确实推进了它。

**排序与截断**：按 `idleDays` 降序，取前 10 条（`?limit=` 可调，上限 50）。同时返回各类别的陈旧总数 `byType`，让"你有 37 个未解决问题，其中 12 个超过一个月"这类事实可见——**汇总比清单更能说明问题**，因为清单只能显示 10 条。

**空态**：没有陈旧记录时返回空数组，前端显示「近期都在推进，没有陈旧记录」而非空白卡片。

### ADR-010 · 心愿单条目管理移至专页，首页只留汇总

**背景**：原设计首页区块 C 同时承载"三项汇总 + 完整条目列表 + 勾选 + 快速新增"。随着条目增长，这一区块会越来越长。

**决策**：首页 C 只保留**三个数字 + 一根进度条**；条目列表、勾选已购、排序、快速新增全部移到 `wishlist.html`（§0.2.4）。

**理由**：

1. **首页的定位是"一眼看完"**。区块数量已经是首屏能承载的上限，其中一个区块无限增长会破坏这个前提。
2. **汇总比清单更有决策价值**。看到"还差 ¥4,776"会影响行动；看到 20 条想买的东西不会。首页应该只留前者。
3. **勾选购买是需要专注的操作**，误触代价高（金额划错、汇总跟着错），不该和一个信息展示区混在一起。
4. **进度条提供了清单之外的新信息**：已花占总额的比例，这个"完成度"在纯列表里看不出来。

**接口无需改动**：`GET /api/wishlist` 已同时返回 `items` 和 `summary`。首页取 `summary` 忽略 `items`，专页两者都用。**不要**为此新增"只返回汇总"的端点——本地服务传输几 KB 的 items 数组没有意义，多一个端点反而增加维护面。

**将来若还要加看板**：新建 `stats.html` 统计页承载，首页保持现有区块数量不再增长。首页每加一个区块，被认真看的概率就下降一分。

### ADR-011 · 随机灵感与随机知识点合并为一个区块

**背景**：原设计首页 D（随机灵感）、E（随机知识点）是两个独立区块。二者**完全同构**——只差一个 `type` 参数，渲染逻辑、按钮、空态处理、详情跳转全部一样。

**决策**：合并为一个「随机回顾」区块，顶部 tab 切换 `灵感` / `知识点`。首页区块数由 7 降至 **6**。

**理由**：

1. **消除重复代码**。两个区块意味着 `index.js` 里两份几乎相同的渲染函数、两份"换一条"状态机、两份空态文案。合并后只写一份，用 `type` 参数化。
2. **省出首屏空间**。这是在不减少任何信息量的前提下唯一能压缩首页的做法——两个 tab 承载的信息与两个并排区块完全等价。
3. **符合心智模型**。用户想的是"给我看点沉底的东西"，不是"给我看灵感"或"给我看知识点"；二者是同一意图的两种素材。

**必须注意的实现细节**：

- **两个 tab 各自维护独立的"已看列表"**（`exclude` 参数）。若共用一份，切到知识点 tab 时灵感看过的 id 会被无意义地传进 `exclude`，虽然不影响正确性（后端会忽略不属于该池的 id），但会让 URL 和请求变长，且语义混乱。
- **切换 tab 不应重新抽取**，而是显示该 tab 上一次抽到的内容——否则用户点「换一条」后切走再切回来，刚才看到的那条就丢了。
- 两个 tab 的**空池提示文案不同**：灵感为「还没有灵感，去记一条」，知识点为「还没有碎片知识，去记一条」，且跳转链接的 `type` 不同。

**代价**：知识点比灵感少一个"学科徽标"以外的展示位；两块并排时一眼能看到两种素材，合并后需要点一下 tab。→ 接受。tab 默认停在灵感，且两个 tab 都显示各自的池大小（如「灵感 · 23 条」），信息不丢。

### ADR-012 · 构成环两种维度统一用环形图，但标签维度强制 Top N 聚合

**背景**：区块 E 支持「按学科」「按标签」两种维度，用滑块切换。学科通常 5~10 个，标签是自由文本、每条记录最多 20 个、全局无上限。

**决策**：两种维度**都渲染为环形图**，切换时只换数据源与配色，图表类型不变。**但标签维度必须做 Top N 聚合**：

- 取计数最高的 **8 个**标签各占一片
- 其余全部合并为一片，标签显示为「其他 N 个」，值为这些标签的计数之和
- 学科维度同理：一级学科超过 8 个时也做相同聚合（虽然实际很少超过）

**为什么必须聚合**：环形图的可读性上限约为 **8~10 片**。超过之后切片窄成一条缝，图例互相压盖，颜色也无法区分——图表还在，但已经不提供任何信息。标签数量完全不可控（用户随手就能打到 30 个），不聚合的话切到标签维度必然得到一团看不清的东西。

**"其他 N 个"是否丢失信息**：长尾标签的单个计数通常是 1~2，它们的价值在于**总和**（"我有 17 个标签只出现过一两次"本身就是一个值得知道的事实），而不是逐个列出。因此合并为一片恰好保留了有用信息，去掉的是噪音。

**聚合在前端做，不在后端**：`meta/tags` 仍返回全部标签及计数（列表页筛选器需要完整列表），前端取前 8 个渲染、其余合并。**不要**为此给端点加 `?limit=` 参数——那会让筛选器拿到不完整的标签列表。

**配色**：环形图切片需要一个稳定的调色板（8~9 色）。定义在 `css/tokens.css` 的 `--chart-1` ~ `--chart-9`，明暗主题各一套。**「其他」片固定用中性灰**，不参与主题配色轮换——它在视觉上应该退后。

## 0.6 术语表（Glossary）

统一用语，避免代码与文档中同义词混用。

| 术语 | 英文/代码标识 | 定义 |
|---|---|---|
| **记录** | `Record` | 四个类别下的一条学习记录，是本系统的主要数据实体 |
| **类别** | `Category` / `type` | 记录的四种归属之一：`inspiration`（灵感）、`question`（问题）、`knowledge`（碎片知识）、`todo`（要做的事） |
| **学科** | `subject` | **仅碎片知识**具备的二级分类维度，如 `数学`、`数学/线性代数`、`英语` |
| **标签** | `tag` | 跨类别的自由分类维度，一条记录可有 0~N 个，字符串数组 |
| **笔记** | `Note` | 挂在某条记录下的追加想法，带独立时间戳，可多条，**不修改原正文** |
| **状态** | `status` | 记录的生命周期标记，取值随类别而异，见 01 §1.4 |
| **心愿条目** | `WishItem` | 心愿单中的一项，含名称与金额，可标记为已购 |
| **已购** | `purchased` | 心愿条目的布尔标记，为真时金额在 UI 上加删除线 |
| **看板** | Dashboard | 首页，聚合呈现统计、心愿单、随机回顾 |
| **随机回顾** | Random Recall | 首页区块 D 的机制：随机抽取一条灵感或知识点呈现，tab 切换两种素材 |
| **陈旧记录** | Stale Record | 超过类别阈值未被推进的记录，见 ADR-009。由区块 F 呈现 |
| **构成环** | Composition Ring | 首页区块 E，碎片知识按学科或标签的占比环形图 |
| **数据根** | `dataDir` | 存放 5 个 JSON 文件的目录，默认 `data/`，可用 `--data=` 覆盖 |
| **静态根** | `webDir` | 存放前端资源的目录，默认 `web/`，可用 `--web=` 覆盖 |
| **备份区** | `.backup/` | 数据根下的隐藏目录，存放写入前的自动快照 |

**易混淆点，特别说明**：

- **「学科」≠「标签」**。学科是碎片知识的**结构化必填字段**，用于筛选下拉框，取值应保持稳定；标签是**自由文本数组**，用于横向关联，允许随意增删。不要用标签存学科。
- **「笔记」≠「正文」**。正文（`content`）是记录本身，编辑会覆盖；笔记（`notes[]`）是追加式的，只增不改（可删单条）。详情页两者分区呈现。
- **「心愿条目」不是「记录」**。心愿单是独立数据域，有自己的文件、模型和端点，**不复用** `Record`。它不参与类别统计，不出现在随机回顾里。

**需要手动获取的四个第三方文件**（获取步骤与下载地址详见 05 §5.2）：

1. `gson-2.11.0.jar` → 放入 `server/lib/`（后端 JSON 序列化）
2. `chart.umd.min.js` → 放入 `web/vendor/`（环形图）
3. `marked.min.js` → 放入 `web/vendor/`（Markdown 解析）
4. `purify.min.js` → 放入 `web/vendor/`（**HTML 净化，XSS 防护必需项**，见 04 §4.9.1）

四者均为本地文件引用，运行时**不访问任何外部网络**。
